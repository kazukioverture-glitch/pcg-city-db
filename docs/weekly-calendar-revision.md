# 2027 S1 シティリーグ週次集計の改訂（2026-10-11）

## 採用する週次定義

- **2027 S1 / 月曜00:00〜日曜23:59（日本時間）**。大会の**実開催日**で判定。
- W01 = 2026-09-21〜09-27（最初の大会は09-26）。
- W02 = 2026-09-28〜10-04。
- W03 = 2026-10-05〜10-11。
- W04 = 2026-10-12〜10-18。以降は7日ずつ。
- Top8・Top16は同じ週次境界、同じ収集処理を使用し、重複加算しない。
- 収集スケジュール（JST 08:00/18:00/20:00/22:00/23:00）は変えない。
- 週が終了した次の月曜に未公開結果を確認し、火曜の資料制作を目指す。**週終了と結果の公開完了は別条件**。

## 旧版を残すこと（重要）

既存の W02 FINAL `data/analysis/weekly_snapshots/W02/FINAL/c2931ef42b944a3e86536742089d0c3f` は **2026-09-30〜10-06** の不変入力として保存する。既存のW01資料・予測原文・回答インデックスも上書きしない。今回の再集計はあくまで**新しい期間定義の版**で、古いFINALを黙って読み替えない。

元のW01/W02と新しいW01/W02は同じラベルでも期間が異なるため、数値の比較・後追い検証には **calendar_id** を必ず併記する。過去の予測は作成時の対象週と利用可能情報を固定し、必要な場合のみ別途週対応表を持たせる。予測を事後編集しない。

## 現行GitHub DBの読み取りで確認した例

データ更新 2026-10-10 22:48:50+09:00 時点、**オープンの公開結果捕捉行**：

| 週 | 旧：水〜火 Top8 | 新：月〜日 Top8 |
|---|---:|---:|
| W01 | 536 | 496 |
| W02 | 616 | 608 |

数字は集計時点の違いで変動しうる。元のW02 FINAL（2026-10-07 01:20の入力）では旧W02は608、新W02は600。**異なる入力時点を混ぜて増減分析しない。**

Top16は独立した全参加者の使用率ではない。9〜16位までの公開行を取得でき、完全性を確認できた大会のみ分析対象とする。Top8との比較では**同一大会のTop8**を分母・比較対象として扱う。Top16分析に含められない大会は欠損扱いにする。

## 再集計の方法

実装：
- `analysis/week_calendar.py`：唯一の月〜日境界定義、実開催日→週番号。
- `analysis/restate_calendar.py`：既存の公開結果DBとデッキDBを再利用し、新W01/W02の**別版**レポートを生成。既存のスナップショットや予測原文は書き換えない。
- `.github/workflows/weekly-calendar-restatement.yml`：ユニットテスト・再計算・監査の後、出力をコミット。入力Git SHAとファイルSHA256を保存。

実行例：

```bash
python -m unittest discover -s tests -v
python -m analysis.restate_calendar --weeks W01 W02
```

結果は `data/analysis/weekly_restatements/2027-s1-mon-sun-v1/<source_git_sha_12桁>/W01/report.json`（W02も同様）と、要約用 `manifest.json` に保存する。**RESTATEDはFINALスナップショットとは異なる**。FINAL入力の厳密な再固定は別の手順で行い、既存版の変更は禁止する。

デッキ名分布、構築・カード採用、Top8→Top4→Top2、Top16の一致大会比較、全国と愛知県は既存の `analysis.weekly` を使用して再計算する。現在のTop8・Top16収集を重複起動しない。

## 移行後の境界

- CURRENT_WEEKは1週の月〜日だけ。
- TRENDは直前の月〜日を独立に抽出。累積値を流用しない。
- 旧版W01/W02との比較は禁止（定義不一致）。旧版の数値を並べる場合は「旧定義」と明記。
- カバレッジは実際の公開結果大会数とTop16完全捕捉大会数を別記。予定開催全件の捕捉率は本再集計だけでは判定不能。
- 事実分析・外部考察・予測を混合しない。
