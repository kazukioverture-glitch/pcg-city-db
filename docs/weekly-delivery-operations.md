# 毎週の分析を期限内に出す運用

基準: main `44ad88903c45d4008d87b4ee9fce5f317c7e6d9a`、2026-10-17。
目的は取得可能な結果を集め、残った欠測の影響を明示して毎週成果を出すこと。全件検収・FINALを定時版の発行条件にしない。欠測の削除、0埋め、中止の推測はしない。

## 週の流れ（JST）

| 時点 | 作業・成果 |
| --- | --- |
| 大会日〜翌朝 | 既存のTermux公式収集5回/日とActions転送5回/日を維持。取得済みデッキは再利用。新規/未取得大会・デッキを優先する既存の有限バッチを使用 |
| 月曜 | 通常収集で残件補完。未取得結果→未取得60枚→Top16の順で診断。403/429は連打せず、404も未開催とは扱わない |
| 火曜08:00 | 通常の最終転送枠。追加の全件収集は起動しない |
| 火曜10:00 | `weekly-delivery.yml`が直前の終了週を自動選択し、固定Git版からJSON・Markdown・欠測感度を生成、保存。Actions summaryとartifactにも掲載 |
| 火曜12:00目標 | 定時版を用いた資料化。PNG/PDF・外部記事調査・MDM全5軸の自動完成は今回未実装。これらを理由に数値版の出力を止めない |
| 後日 | 重要な補完が得られた週のみ、明示した週で定時版を再生成。別の入力版として保存し旧版を保持。旧FINAL・予測原文は変更しない |

GitHub cronの開始遅延・障害、Androidの省電力停止・再起動復帰は保証できない。10時は設定時刻であり配信保証ではない。失敗時はActionsがFAILになり、診断artifactを残す。完全無人の復旧は保証しない。

## 出すもの・止めるもの

- 正常な入力と1行以上の対象Top8があれば、監査WARNでも「取得済み公開結果・INTERIM」の定時版を出す。全国全件取得済み、母集団の使用率、対戦勝率とは表記しない。
- 入力破損・SHA256/件数不一致・監査FAIL・対象結果0件は分析公開を止める。前回資料を新しい週の結果として流用しない。失敗診断と不足状況を残す。
- 更新時刻、24時間超の古さ、週末以降に更新されたかを明記。新しい転送時刻だけで結果が新しいと判断しない。
- Top16は完全取得大会集合だけ。同じ大会集合のTop8と比較し、全Top8の母集団と混ぜない。地域の欠測は全国平均で薄めず、該当地域の結論を保留する。
- Performanceは既存の実績計算を利用。Attention / Social Proof / Adoptability / Strategic Responseの外部根拠と、予測は別工程。外部考察を今回の定時版で実施済みと表示しない。

## 欠測を切り上げる判断

「大きいデータだから少数の欠測は無視できる」とは判断しない。特定地域・日付・カテゴリ・デッキに欠測が偏る可能性がある。

1. 取得できた正常行を保護し、未取得大会ID・短いTop8結果・未分類を別記する。短い結果は正当な公開範囲かもしれず、欠測確定ではない。
2. 台帳内の対象/カテゴリ不明大会について「1大会Top8は最大8枠」という条件で潜在欠測Mを計算。取得済みN行、未分類U行、特定親分類k行なら構成比の感度は `k/(N+M)`〜`(k+M+U)/(N+M)`。実際の順位行が8を超える制度・未記録大会にはこの条件を適用できない。
3. これは信頼区間や無作為欠測の仮定ではない。未記録大会数が不明なら全国欠測の上限は不明のまま。計算で台帳網羅性を認定しない。
4. 欠測/未分類が全て一方の親分類へ入っても順位差が逆転しない等、結論が条件付きで維持できる部分は注記して記載。逆転し得る順位・僅差・前週差は断定しない。前週差は前週側の欠測も別途評価する。
5. 結論に影響し得る項目だけ、HTTPエラー別の既存上限内で対象ID/デッキコードを再確認。期限までに解消しなければ、その結論を保留して発行する。「切り捨て」はその週の追加調査の打切りであり、DBや取得履歴の削除ではない。

W03については定時運用への移行例としてのみ検証する。未取得大会や短い結果の原因は不明のまま保持し、FINALを自動宣言しない。

## 実行・最小復旧

GitHub Actions → **Weekly observed-results delivery** → Run workflow。通常は週欄を空欄にする。過去週を補完した場合のみ `W03` 等を明示する。main上の正常DBを読み、追加API取得はしない。

```sh
# 開発時の高速検査（通信なし）
python -m unittest discover -s tests -p 'test_weekly_delivery.py' -v
# cleanな固定Git版で生成。既存本番データには書き込まない
python -m analysis.weekly_delivery --week W03 --output-root .tmp/weekly-delivery-check
```

保存先は `data/analysis/weekly_deliveries/<calendar_id>/<week>/<generation_id>/`。入力5ファイルと分析器版から世代IDを計算し、同じ入力の再実行は既存結果を再利用。ディレクトリを完成させてから公開する。workflowは収集と同じ排他グループで動かし、本番同期を追加起動しない。push競合はforceせず失敗診断を残す。

通常収集失敗時は既存の[収集復旧手順](collection-operations.md)に従う。Androidでの収集が必要な場合だけ `bash scripts/termux_refresh.sh once` を1回実行する。単なる再分析では不要。配信URL変更時だけRepository Variableを修正する。

失敗を確認したら原因を修正して対象週を1回再生成。入力破損を無視するオプションはない。取得不可の影響が大きければ、定時版の対象範囲を狭めるか該当する結論を保留する。

## 検証・負荷

既存収集回数・公式API上限・Termux運用を変更しない。追加は分析workflow週1回、追加公式HTTPリクエスト0、本番DB書込み0。同一入力なら追加成果物commit0。初回のみJSON/Markdownの小さな派生成果物を保存。数値資料の自動作成と、スマホ向けPNGの自動完成は区別する。

関連テスト→全体Analysis CI（旧FINALスモーク含む）→差分監査の順。既存FINAL、予測、入力履歴、分類ルールは対象外。定期実行の本番検収と実行時間・生成バイト数は反映後に別途記録する。

## 出力資料の編集方針（2026-10-17改訂）

読者向けの`report.md`と、これを基に作るPNG/PDFには、未実施・未検証・未取得等の作業状況や監査WARNを掲載しない。対象期間、集計対象、分母、比較条件、信頼区間など数値の定義は残す。根拠のある結果だけ掲載し、空の分析欄や不足説明は省略する。分類未確定の行は読者向け構成表では「その他」として分母に残す。

内部の`report.json`・`summary.json`には監査、欠測感度、鮮度、未分類、FINAL状態を引き続き保存する。資料の表現変更で監査判定や公開停止条件は変えない。資料にFINALと記載するのは別途確定した場合のみ。
